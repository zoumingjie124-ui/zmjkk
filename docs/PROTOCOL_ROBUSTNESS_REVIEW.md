## A. 帧内无超时 —— 一个丢失字节可以吃掉整条后续命令（P1）

> **状态：已修复（2026-10-30，第五轮）**。下面保留问题分析与复现步骤原文，便于核对"修复是否对症"；修复内容见本节末尾。

**代码（修复前）**：`comm.c` 的 `PS_PAYLOAD` 分支只按 `s_idx >= s_len` 推进，没有任何时间判断；`Comm_Tick()` 里也没有"多久没收到新字节就复位"的逻辑。

**机理**：

1. 一帧在传输中丢掉 1 个字节（线路噪声、或 B 项的缓冲溢出），解析器停在 `PS_PAYLOAD`，`s_idx < s_len`。
2. 解析器**无限期等待**剩余字节，没有超时。
3. 下一条合法命令的字节被当作"上一帧的剩余载荷"吞掉，直到凑满 `s_len` 个字节。
4. 凑满后算 CRC → 必然不符 → 回 `NACK(1)` → 复位。
5. 结果：那条合法命令**没有执行、也没有应答**，主机只看到一个莫名其妙的 CRC 错误。

`PROTOCOL.md` 原先写的"最坏情况丢弃当前帧，下一帧自动恢复"——**只在 LEN 字节凑满之后成立**。若 LEN 声明为 32 而主机之后停手不发，解析器就一直卡着；若主机是"发一条等一条"的 300ms 节奏，那一条命令就白发了。

**复现步骤**（用 `host/protocol.py` 组帧，或手搓字节）：

```text
第 1 步：发 AA 55 02 20 00              (SET_TARGET，声明 LEN=32，只给 1 字节载荷，然后停手)
第 2 步：发 AA 55 01 00 <crc_l> <crc_h> (一条完整的 GET_STATUS)

修复前：收不到 0x81，而是收到 0x7F 01（NACK CRC 错误）——STOP 同理会被吞掉
修复后：第 2 步正常收到 0x81；半帧在 50ms 后被静默丢弃
```

**上板验收脚本**：`host/repro_truncated_frame.py`

```bash
python host/repro_truncated_frame.py --port COM5 --dry-run   # 只看要发的字节，不连接
python host/repro_truncated_frame.py --port COM5             # 期望：不再观察到 NACK(1)
```

**判定**：协议层健壮性缺陷。C 实现里没有帧内超时，而 Python 侧的 `t3_roundtrip_and_split` 只测了"跨两次 feed 的正常帧"，测不出这个场景——这也是"Python 测过 ≠ C 写对了"的典型。

**修复记录（2026-10-30）**：

| 项 | 内容 |
|----|------|
| 实现 | `App/Src/comm.c` 新增 `FRAME_GAP_TIMEOUT_MS = 50`；`Comm_Tick()` 在排空循环之后，若 `s_ps != PS_H1` 且距最后一个字节 ≥50ms，则 `parser_reset()` |
| 时间戳 | 每收到一个字节刷新 `s_last_byte_ms`；判定时**重新取一次 `HAL_GetTick()`**，避免用循环前的旧 `now` 与最新时间戳相减导致无符号下溢 |
| 超时动作 | **静默丢弃半帧、不发 NACK**：此时上位机正在等响应，多一条 NACK 只会与新帧交错；丢失由上位机 300ms 重发兜底 |
| 阈值依据 | 115200 8N1 每字节约 87µs，最长帧 38 字节 ≈ 3.3ms；50ms 是 15 倍余量，又远小于上位机 300ms 重发超时 |
| 回归测试 | `tests/test_comm.c`（T3 截断后 STOP 必须执行、T4 49/51ms 边界、T6 超时后载荷不被污染）共 18 项 |
| 反向验证 | 临时把超时分支改成永不成立 → T3 出现 4 项失败，其中 `STOP executed (0)` 正是本项描述的后果；恢复后全过 |
| 待验证 | **上板**跑 `repro_truncated_frame.py`，判据是"不再观察到 NACK(1)" |

## B. 吞吐上限低于线路速率（P1）

**代码**：`comm.c:344` `while (guard++ < 64u && Usart_ReadByte(&b))`；`main.c:97` 通信时间片 **10ms**。

**计算**：

| 项 | 数值 |
|---|---|
| 每 tick 最多消化 | 64 字节 |
| tick 周期 | 10 ms |
| 有效吞吐上限 | 64 / 0.01 = **6400 B/s** |
| 115200 8N1 线路速率 | 115200 / 10 = **11520 B/s** |
| 缺口 | 约 **1.8 倍** |

只要主机持续以全速灌包（压测、或上位机一次连发多条），环形缓冲必然被填满，然后走 `usart.c:63` 的 `s_overflow++` 丢字节——丢字节就会触发 A 项的截断。

**复现步骤**：Python 以 115200 连续发 200 条 GET_STATUS（不等应答，间隔 2ms），统计收到的状态帧数量。预期 200 条，实际会明显少于 200 条。

**判定**：不是"偶发"问题，是结构性上限。单条命令的实际使用没有问题（人不会手速发 200 条），但压测脚本会稳定撞上。

## C. 溢出计数没有消费者（P1）

**代码**：`usart.c:90` 定义 `Usart_OverflowCount()`，`usart.h:18` 声明，**全仓库没有任何调用点**。

**后果**：

- 溢出发生后，固件自己不知道、不报告、也不复位解析器。
- 与 A 项串联成一条完整的失效链：

```
持续灌包 → 缓冲满 → 丢字节 → 帧截断 → 解析器在 PS_PAYLOAD 无限等待
        → 后续命令被当载荷吞掉 → 主机看到"命令无应答 + CRC 错误"
```

- 上位机侧只能看到"这条命令没回"，看不到"链路上丢了字节"这个根因。`status` 帧 25 字节里也没有溢出字段。

**复现**：`grep -rn Usart_OverflowCount` 只有声明和定义两行，没有调用。

**建议方向**（原方案）：占用状态帧的一个保留字节上报溢出计数，或至少溢出时 `parser_reset()`。

**修复记录（2026-10-30）**：没有动状态帧结构（25 字节载荷已被上位机与 CSV 记录依赖），改为**独立的诊断命令**：

| 侧 | 内容 |
|----|------|
| 固件 | `0x09 GET_DIAG` → `0x89` + 8 字节：`u32 overflow`（环满丢弃字节数）/ `u32 rx_bytes`（累计入环字节数） |
| 上位机 | `protocol.build_get_diag()` / `parse_diag()`（长度不为 8 直接抛 `ValueError`，不返回半截数据） |
| CLI | `monitor_cli.py` 每 5s 拉一次诊断，`overflow != 0` 时打印"曾有溢出丢字节"告警 |
| 测试 | `test_comm.c` T5（固件侧编码）+ `test_protocol.py` T11（上位机侧解码 11 项，含 5 种错误长度） |
| 说明 | 固件**不主动上报**诊断，只有被问才回——避免给正常链路增加流量 |

**仍未闭环的部分**：溢出发生时固件依然不会自动 `parser_reset()`。超时（A 项）已经能把"丢字节 → 卡死"这条链切断，所以没有再加这一步；若要更早恢复，可以后续在 `Usart_RxByte` 的溢出分支里置一个标志，由 `Comm_Tick` 消费。

## D. NACK 不携带原命令号（P2，设计限制）

**代码**：`comm.c:145-148` `send_nack(code)` 只发 `CMD_NACK(0x7F)` + 1 字节错误码。

**影响**：粘包场景下主机连续发了 SET_TARGET、START 两条命令，若收到一个 `NACK(3)`，无法判断是 SET_TARGET 越界还是 START 被拒。上位机只能"整批重试"或"整批放弃"。

**判定**：与 `PROTOCOL.md` §1 的帧格式一致，属既定设计。若以后要做自动重试策略，建议改成 `NACK` 载荷 2 字节：`[原 CMD][错误码]`。

## E. 未知命令复用 `LEN_ERR(2)`（P2，设计限制）

**代码**：`comm.c:238-240` `default: send_nack(ACK_LEN_ERR);`

**影响**：主机收到 `NACK(2)` 时分不清两种完全不同的情况：

| 情况 | 主机正确反应 |
|---|---|
| LEN 超 32 / 载荷长度与命令不匹配 | 修载荷、重发 |
| 命令字不认识（固件版本旧） | **停止重试**，升级固件 |

现在两种情况都回 2，主机若统一"修了再重发"，遇到未知命令会无限重试。

**判定**：与文档 §1 错误码表一致（2 已涵盖未知命令），所以不算实现与文档不符，但建议加 `7 = 未知命令`。

## F. STOP 后立即关风扇，STANDBY 不管理风扇（P2，已定策略并实现）

**代码**：

- `control.c:143` `Control_Stop()` 里 `Fan_Off()`
- `control.c:219-228` `CTRL_STANDBY` 分支只调 `Heater_Off()`，注释写"风扇状态由 STOP/故障确认时已置于关闭"

**场景**：RUNNING 加热到 60℃ → 发 STOP → 风扇立刻停 → 加热器余热使温度继续上冲，只能一路涨到 75℃ 触发 `safety_interlock` 进 FAULT，然后风扇才被强制打开。

**为什么算问题**：故障态的联锁是"最后一道防线"，不应该被用来兜"正常停止后的散热"。用一次 STOP 就换来一个 FAULT，会让 FAULT 失去诊断价值（`fault` 字段看不出是过热还是人为停止留下的余热）。

**判定**：可能是刻意取舍（避免风扇常开）。当时的两个候选：① 接受，在 README 的"已知限制"里写明；② STANDBY 里补"温度 > 目标+2℃ 则开风扇"。**结论选 ②**，详见下方。

---

**策略已定（2026-10-30）**

| 项 | 决定 | 理由 |
|----|------|------|
| STOP 的动作 | **只关加热**（PWM=0 + 关输出许可），**风扇保持当前状态** | 停机瞬间温度仍高，立刻停风等于把余热闷在腔体内 |
| STANDBY 的风扇 | 沿用与 RUNNING **完全相同的迟滞**：`T > target+2.0℃` 开、`T < target+0.5℃` 关 | 判据只有一套，不会出现"运行期在吹、停机后反而不吹"的矛盾 |
| 什么时候真停 | 温度回落到 `target+0.5℃` 以内自动停 | 与运行期一致，用户只需看 FAN 一栏 |
| 故障时 | FAULT 仍是风扇常开（不变） | 故障散热优先，不允许被余热逻辑干扰 |
| 为什么不加超时 | 温度是有效读数，吹风本身是安全动作；环境温度本就高于目标时持续吹风是正确行为 | 加超时会掩盖真实高温 |

**实现**：抽出 `fan_hysteresis(temp_c)` 供 RUNNING/STANDBY 共用；`Control_Stop()` 删除 `Fan_Off()`。
**测试**：C13（STOP 后 PWM=0 且 FAN 保持；46.5℃ 保持、45.2℃ 关闭；本来就凉则不开）。
**对外可见的行为变化**：`STOP` 后上位机可能看到 `FAN=ON`，已写进 `PROTOCOL.md` 的 STOP 语义说明，避免被当成"没停干净"。

## G. SET_TARGET / SET_PID 把状态错误吞成参数错误（P3，潜在）

**代码**：

```c
status = Control_SetTarget(get_f32(pl));
send_ack(cmd, (uint8_t)(status == 0u ? ACK_OK : ACK_RANGE_ERR));   /* comm.c:197 */
```

**现状无害**：`Control_SetTarget` / `Control_SetPid` 目前只返回 0 或 1，不会返回 2。

**潜在风险**：将来若给这两个函数加上"FAULT 态禁止改参数"之类的状态校验并返回 2，这里仍会报成 `ACK_RANGE_ERR(3)`，主机会以为是自己填错了值。

**建议**：统一改用已有的 `map_ctrl_status()`（`comm.c:36`），它已经能把 0/1/3/其它 正确映射。
